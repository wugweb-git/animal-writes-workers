# Ingestion audit — 12 Oct 2026

Read-only audit. Nothing was changed. The only things run were the test suite, local DRY_RUN runs and live GETs of the feeds. Evidence comes from `gh run view --log` (sourcing runs 9–12 Oct), wp-cli reads on the server and live feed fetches made at about 07:50 UTC on 12 Oct.

## What happened on 10–12 Oct

- 14 scheduled sourcing runs between 38008641297 (10 Oct 00:20 UTC) and 38210043089 (12 Oct 05:54) all ended green. Every one reported `new=0`, and every item it fetched was a `duplicate` (fetched counts were 25–32 per run).
- In 3 days only one item got as far as the relevance gate and a summary (run 38115753445: gate pass=1, gemini=1). The site answered `duplicate` for it.
- On the site, the last News item created was #10870, on 10 Oct at 04:17. There are no pending items, and nothing was held or rejected.
- **Root cause:** Google News search RSS (no `when:`) is ordered by relevance, not by date. `sources.collect()` keeps `fresh[:limit]` (sources.py:278) **before** the seen-check (run.py:122). That means the same 15 old "most relevant" stories are taken every run and are all already seen. Fetched live today, `gnews-animal-welfare` returned 100 items, and **none** were dated 10–12 Oct (newest 9 Oct). `gnews-animal-cruelty` had nothing newer than 30 Sep. Every other source genuinely had nothing new (see the coverage table).

## Ranked problems

1. **Cap applied before the seen-check, in relevance order (the outage).** sources.py:278 `fresh[:limit]` runs before run.py:122.
   - Impact: any feed with ≥15 seen items can never deliver anything new.
   - Fix: in `collect()` sort `fresh` by date (newest first) before capping. In `run()`, drop seen URLs first and then apply `limit` to unseen items. Raise `max_items_per_source` to 40 for `gnews-kw-*`.
2. **Google News 503 from GitHub runners, and runs stay green.**
   - Evidence: run 38219652529 (dry, 07:46 UTC) had 23 of 29 sources fail with `503 Service Unavailable`. All of them were Google, including the very first request. The same URLs return 200 locally. Result: `failed=23`, conclusion **success**, because run.py:347 exits 1 only when nothing at all was duplicate/skipped.
   - Fix: count Google failures separately. Exit non-zero, and call `client.ingest_heartbeat(new, failed=…)`, when ≥50% of sources fail. Retry 503 with backoff and add a small delay between Google requests. Send a browser-like UA. Add a fallback through Bing News RSS.
3. **The 20-minute job timeout loses all state.**
   - Evidence: the local DRY_RUN with no LLM calls took **608 s** (enrichment means 3 HTTP calls per item). Live adds about 3 LLM calls per item (Groq min interval 3 s, 429 backoff 10/20/40 s, 60 s read timeouts seen in run 38202525124).
   - Impact: the first live run will probably exceed `timeout-minutes: 20`. `save_seen`, `save_titles`, `gate.save()` and the heartbeat all run only at the end (run.py:316, 331), so each run redoes the same items and no heartbeat is sent.
   - Fix: save state after each POST (or in `try/finally`). Add a 15-minute time budget that stops cleanly. Set the timeout to 45. Run the animal-word guard **before** `enricher()` (run.py:127 vs 139): that saves 46 wasted resolves per run.
4. **The heartbeat can't catch a dead pipeline, and counts the wrong thing.**
   - Evidence: option `aw_ingest_heartbeat` doesn't exist yet, because no live run has reported since the deploy. The alert is evaluated only when a worker POSTs (relevance.php:330–361). Timeout, crash, AuthError (`return 3` at run.py:292/307), Actions minutes running out or a cron that never fires all mean **no email**. `new` counts items created as *pending* (held), not published.
   - Fix: add a site-side WP-cron check, `aw_ingest_watchdog` (hourly):
     - alert if the newest *published* `aw_news` is older than 12 h, or
     - `last_run` is older than 8 h.
   - Also send `published` rather than `created` from ingest (return `review` in the response).
5. **The LLM capacity is not there.**
   - Evidence (run 38200889399): openrouter 402, deepseek 402, minimax 402, xai 403, gemini 403 and 429, openai 429, moonshot 429, haiku "credit balance too low". Only Groq works, and it left **116 of 240 items unavailable** in 22.8 min.
   - Expected load: about 68 items on the first run and about 35/day after, at about 3 calls each. That is ~100–150 calls and ~100–150k tokens per day against Groq's free 8k TPM / 200k TPD. `GroqBackend` uses `max_tokens: 300` on a reasoning model, which risks empty replies.
   - Fix: put credit on one paid key (OpenRouter or DeepSeek, about $1/month at this volume) and move it first in `LLM_PROVIDERS`. Merge the topic pick into the relevance call (it already returns `category`). Use `max_tokens` 800 for gpt-oss. Don't mark a key dead on a single 429 (summarise.py:260).
6. **Auto-review holds most new items.**
   - Evidence: auto-review.php:50 holds any publisher that isn't `allow` (64% of fresh stories), then requires keyword strong/animal+context.
   - Fix: when the gate passed with `india=true`, treat neutral publishers as allowed. Alternatively, auto-allow a host after 3 gate-passed items.
7. **Settings → Sourcing is ignored.** `aw_sources.live = false`, so the logs say "lists: from sources.yaml". Keyword edits made on the site do nothing. Fix: turn on "Workers use these lists", or remove the screen.
8. **Cache loss would bring trashed items back.** `aw_find_by_source` uses `post_status any` (ingest.php:42), which excludes **trash**, and 266 items were trashed today. Fix: include `trash` in both duplicate lookups.
9. **Near-duplicate merge is loose.** Jaccard ≥0.45 on title words over 7 days (auto-review.php:101) can merge different "stray dog attack in X/Y" stories. Raise it to 0.6 and require the same place.
10. **Dates.** An auto-published item keeps its *ingest* time as `post_date` (auto-review.php:149), but approval and backfill use the source date. Set `post_date` to the source date.
11. **Gaps.**
    - Gazette weekly "Multiple Ministry" rows: fix by checking the subject only.
    - The `court-news-animals` OR query: split it into per-site queries.
    - `keyword_searches` fetches `"animal welfare"` and `"animal cruelty"` twice: dedupe by URL.
    - Animal words to add: blackbuck, orangutan, antelope, nilgai, hornbill, gharial, otter, `\w+s` plurals generally.
12. **Limits.**
    - Private repo: 743 billable minutes in 3 days, and sourcing will grow to about 15–25 min per run, so check the Actions minutes quota.
    - GitHub ran sourcing 5–7×/day instead of 8 (delays up to about 3.5 h).
    - wp-cron (`*/15`) ran about 5×/day, with one 403 (run 38169232921).
    - No tests cover `keyword_searches`, the heartbeat or the alert.

## What works

- Auth, the policy endpoint, relevance-config and the deployed site files all match the repo (md5 checked).
- Feeds parse: AWBI, LiveLaw, Bar & Bench, The Hindu, eGazette (TLS bundle) and the SC parquet. Their zeros are genuine.
- Seen-state persists between runs (cache seen-* ~400 KB). Items are marked seen only after a POST or a deliberate skip, and `unavailable` and failed items are retried.
- Title dedupe (exact normalised title ±1 day) is not too aggressive.
- Policy: 3 blocked publishers, keyword filter off, so it isn't over-filtering.
- 88 tests pass. Images: 624/760 published News items have a publisher image. Card fallback was fixed in ba9c517 (deployed).
- `when:2d` keyword searches find about 164 fresh stories in 48h, so the sourcing idea is right once problems 1–5 are fixed.
